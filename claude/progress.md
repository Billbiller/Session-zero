What the app does today
Session Zero is a Next.js + TypeScript + SQLite app for finding a D&D (or other tabletop) group and tracking a campaign once you're in one.
Real authentication (backlog #2 — done 2026-09-02): a tabbed sign-in/create-account page (`/signin`) backed by `app/api/auth/signup/route.ts` and `app/api/auth/signin/route.ts`. Accounts are stored with a `bcryptjs`-hashed password (`bcrypt.hashSync(password, 10)`); `lib/auth.ts`'s `signUp()` validates a non-blank display name, a password of at least 8 characters, and a not-already-taken (case/whitespace-normalized) email before creating the account, while `signIn()` looks the account up by normalized email and rejects with `AuthError` on an unknown email or a `bcrypt.compareSync` mismatch — the same generic rejection either way, so sign-in doesn't reveal whether an email is registered. Session cookies/tokens are unchanged from the placeholder scheme (`createSession`/`getUserBySessionToken`/`destroySession`); every user-lookup query now explicitly selects columns and excludes `password_hash`, so a hash can never leak into an API response or a rendered page.
Once signed in, a DM can create a campaign (title, description, system, capacity) and players browse/filter (exact `system` match)/sort/paginate the list and request to join. The DM approves or declines requests; the party auto-fills (closes to new requests) once capacity is hit and auto-reopens if someone leaves, or the DM can manually reopen a full campaign to accept more requests without anyone leaving first. The DM can also cancel/un-cancel a campaign (notifying the active party on cancel) and edit its details after posting (capacity can't be dropped below the current approved headcount — validated).
An approved, non-DM member can leave a campaign (with a confirm step in the UI). Leaving marks their membership `left`, re-runs the auto-reopen-if-under-capacity logic, and immediately revokes their access to the campaign's private side.
Once approved, players and the DM get access to the private side of a campaign: a session log the DM can post to, edit, or delete; a next-session date (stored as a UTC instant, with a computed unscheduled/upcoming/past-due status, compared in UTC so it's timezone-safe); and shared party notes (DM + active members can edit). All of this is hidden from strangers, pending requesters, left members, and signed-out visitors — this boundary has explicit regression tests at both the unit layer (`hasPrivateAccess`) and the HTTP-integration layer (driving a real running server with independent per-role cookie jars, checking both API status codes and that the rendered HTML doesn't leak private content to unauthorized viewers).
Everyone gets in-app notifications for the things that affect them, visible in an inbox page (`/notifications`) with an unread badge in the nav bar (polled every 15s — see backlog #6e for the live-push follow-up). The notification types the app defines (`lib/types.ts`): `join_requested`, `join_approved`, `join_declined`, `member_left_dm`, `member_left_party`, `party_notes_updated`, `session_log_posted`, `schedule_updated`, `campaign_cancelled`.
Notification completeness (6a/6b): leaving a campaign notifies the rest of the active party (DM + other approved/active members), not just the DM — `leaveCampaign()` fans a `member_left_party` notification out to every other approved/active member (DM and the leaver excluded; the DM gets their own separate `member_left_dm` notification). Editing the shared party notes notifies the rest of the active party symmetrically (notes are editable by DM + active members — a deliberate judgment call carried over from earlier sessions — so whoever edits notifies everyone else in the active party except themselves).
Per-notification-type preferences (6d): a signed-in user can mute any individual notification type from a settings page (`/settings/notifications`) so that type is never created for them again.
* A `notification_preferences` table keyed by `(user_id, type)` with an `enabled` boolean, defaulting to enabled for every type when no row exists.
* Enforcement lives in `lib/notifications.ts`'s `notify()`/`notifyMany()` — the single choke point every fan-out path goes through. A muted type is checked before the row is ever inserted, so nothing is written for that user (as opposed to writing it and filtering at read time) — the unread badge count and the inbox list are correct for a muted user with zero extra filtering logic anywhere else, at the cost of not being able to later "unmute retroactively" and see history for the period it was muted.
* `app/api/notifications/preferences/route.ts` (GET the full map + human labels, PUT to toggle one type) is the server-side surface; `app/settings/notifications/page.tsx` is the toggle UI.
Live notification push (6e — done 2026-09-02 nightly build): the unread-badge count in `NavBar` no longer relies solely on a 15s poll. `lib/notificationEvents.ts` is a single in-process `EventEmitter`-based pub/sub (one channel per user id); `notify()`, `markRead()`, and `markAllRead()` in `lib/notifications.ts` all publish the user's fresh unread count to it after writing. `app/api/notifications/stream/route.ts` is a `GET` SSE endpoint (auth required, same `requireUser()` as the other notification routes) that sends an immediate unread-count snapshot on connect, then forwards every subsequent publish for that user as an `event: unread` SSE message, plus a comment-line heartbeat every 20s to keep proxies from timing the connection out. `NavBar.tsx` opens an `EventSource` to that endpoint and updates the badge from each `unread` event; if `EventSource` is unavailable (SSR, or a browser/proxy that doesn't support it) or the connection errors out, it falls back to the original 15s-interval polling for that mount (no reconnect/backoff logic on the SSE side — a deliberate scope cut, see session log).
Explicitly not yet done (remaining larger backlog item): email notifications (blocked — no SMTP/provider credentials).

Tooling notes (read this before re-discovering the same issues)
* This is Next.js 16 — the `create-next-app` scaffold drops a `AGENTS.md`/`CLAUDE.md` pointer at the repo root telling you to read `node_modules/next/dist/docs/` before writing code, because App Router conventions keep changing. Confirmed still true this session: dynamic route `params` (and `searchParams`) are `Promise`s that must be `await`ed (`ctx: { params: Promise<{ id: string }> }`), and `cookies()` from `next/headers` is async (`await cookies()`). "Cache Components" (`cacheComponents: true` in `next.config.ts`) is opt-in in Next 16, not default — this app doesn't enable it, so the pre-16 caching model applies and `export const dynamic = "force-dynamic"` on every route handler that touches cookies/the DB is enough (no `"use cache"` directives needed).
* ESLint flat config for `eslint-config-next@16`: current `create-next-app` scaffolds `eslint.config.mjs` using `defineConfig`/`globalIgnores` from the `eslint/config` package plus `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript` sub-path imports — this shape works out of the box with the `eslint@9` that `create-next-app` itself installs; no manual workaround was needed this session (earlier sessions' notes about `eslint-config-next`'s default export shape and pinning `eslint` below `10.x` may be stale for this scaffold version — re-verify if `npx eslint .` breaks on a fresh install).
* `react-hooks/set-state-in-effect`: a `useEffect` whose body calls a `load()` function declared at component scope (needed when a button handler must also trigger the same reload) gets flagged even though `load()` only sets state after an internal `await`. Fix is a scoped `// eslint-disable-next-line react-hooks/set-state-in-effect` directly above the `load()` call — **the disable comment must be the line immediately before the flagged call**; multi-line explanatory comments have to go *above* the disable directive, not between it and the code, or the directive silently doesn't attach (ESLint then reports both "unused disable directive" and the original error). `NavBar`'s polling effect avoids the whole issue by declaring its loader function inside the effect body itself.
* `next build` type-checking test files: `tsconfig.json`'s default `include` picks up every `**/*.ts`/`**/*.tsx`, which pulls Vitest test files into the Next.js build's TypeScript pass and fails it. Fix: add `"__tests__/**"` and `"vitest.config.ts"` to tsconfig's `"exclude"` array.
* `next.config.ts` cannot carry an `eslint` key in this Next.js version — ESLint config now lives solely in `eslint.config.mjs`.
* `@types/react-dom` doesn't publish a version matching `react-dom`'s own version number — let npm resolve `@types/react`/`@types/react-dom` against their own `^19` ranges rather than pinning to the runtime package's exact version.
* `next/font/google` requires outbound access to `fonts.googleapis.com` at build time — fails hard in a network-restricted sandbox. Use system font stacks (or `next/font/local` with self-hosted font files) instead.
* HTTP integration test spawning a real server: spawn the **local** `next` binary directly (`node_modules/.bin/next start`), not via `npx next start` — `npx` forks a wrapper process that doesn't reliably forward a kill signal on to the actual `next-server` child, which left orphaned servers holding the spare port open between test runs (`EADDRINUSE` on the next run). Spawn with `detached: true` and kill the whole process group with `process.kill(-server.pid, "SIGTERM")` in `afterAll`.
* Same-millisecond `ORDER BY created_at DESC` ties need a secondary sort key — see backlog item #14 above.
* Per-test-file isolated SQLite databases: `lib/db.ts` reads `process.env.SQLITE_DB_PATH` at module-load time (falling back to `data/session-zero.db` for the real app). `__tests__/setup.ts` is wired in via `vitest.config.ts`'s `setupFiles` and assigns a fresh `data/test-<uuid>.db` path before that test file's own imports resolve — Vitest isolates each test file's module registry, so this gives every test *file* (not every individual test) its own DB. The HTTP integration test manages its own separate DB file explicitly (passed via `env` to the spawned `next build`/`next start` child processes).
* `package.json` needs `"type": "module"` for `vitest.config.ts`'s `export default` to load natively without a CJS-compat warning; harmless with `next build`/`next lint`/the test suite since every source file already uses ESM syntax.
* `vitest.config.ts` should use `path.dirname(fileURLToPath(import.meta.url))` instead of bare `__dirname`, which Vite's native config loader warns is unsupported and will eventually be removed.
