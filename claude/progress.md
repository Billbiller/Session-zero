**2026-09-07 update (live session, continued): backlog item #35 (session RSVP + reminders) is DONE.** A campaign's active party can now confirm or decline the upcoming `next_session_at` date on the campaign detail page, right below the schedule, and gets a one-time in-app reminder as that date approaches. Reminders were the harder design question: this app has no background job runner or cron, so there's no process watching the clock. What the app does today
Session Zero is a Next.js + TypeScript + SQLite app for finding a D&D (or other tabletop) group and tracking a campaign once you're in one.
Real authentication (backlog #2 — done 2026-09-02): a tabbed sign-in/create-account page (`/signin`) backed by `app/api/auth/signup/route.ts` and `app/api/auth/signin/route.ts`. Accounts are stored with a `bcryptjs`-hashed password (`bcrypt.hashSync(password, 10)`); `lib/auth.ts`'s `signUp()` validates a non-blank display name, a password of at least 8 characters, and a not-already-taken (case/whitespace-normalized) email before creating the account, while `signIn()` looks the account up by normalized email and rejects with `AuthError` on an unknown email or a `bcrypt.compareSync` mismatch — the same generic rejection either way, so sign-in doesn't reveal whether an email is registered. Session cookies/tokens are unchanged from the placeholder scheme (`createSession`/`getUserBySessionToken`/`destroySession`); every user-lookup query now explicitly selects columns and excludes `password_hash`, so a hash can never leak into an API response or a rendered page.
Once signed in, a DM can create a campaign (title, description, system, capacity) and players browse/filter (exact `system` match)/sort/paginate the list and request to join. The DM approves or declines requests; the party auto-fills (closes to new requests) once capacity is hit and auto-reopens if someone leaves, or the DM can manually reopen a full campaign to accept more requests without anyone leaving first. The DM can also cancel/un-cancel a campaign (notifying the active party on cancel) and edit its details after posting (capacity can't be dropped below the current approved headcount — validated).
An approved, non-DM member can leave a campaign (with a confirm step in the UI). Leaving marks their membership `left`, re-runs the auto-reopen-if-under-capacity logic, and immediately revokes their access to the campaign's private side.
Once approved, players and the DM get access to the private side of a campaign: a session log the DM can post to, edit, or delete; a next-session date (stored as a UTC instant, with a computed unscheduled/upcoming/past-due status, compared in UTC so it's timezone-safe); and shared party notes (DM + active members can edit). All of this is hidden from strangers, pending requesters, left members, and signed-out visitors — this boundary has explicit regression tests at both the unit layer (`hasPrivateAccess`) and the HTTP-integration layer (driving a real running server with independent per-role cookie jars, checking both API status codes and that the rendered HTML doesn't leak private content to unauthorized viewers).
Everyone gets in-app notifications for the things that affect them, visible in an inbox page (`/notifications`) with an unread badge in the nav bar (polled every 15s — see backlog #6e for the live-push follow-up). The notification types the app defines (`lib/types.ts`): `join_requested`, `join_approved`, `join_declined`, `member_left_dm`, `member_left_party`, `party_notes_updated`, `session_log_posted`, `schedule_updated`, `campaign_cancelled`.
Notification completeness (6a/6b): leaving a campaign notifies the rest of the active party (DM + other approved/active members), not just the DM — `leaveCampaign()` fans a `member_left_party` notification out to every other approved/active member (DM and the leaver excluded; the DM gets their own separate `member_left_dm` notification). Editing the shared party notes notifies the rest of the active party symmetrically (notes are editable by DM + active members — a deliberate judgment call carried over from earlier sessions — so whoever edits notifies everyone else in the active party except themselves).
Per-notification-type preferences (6d): a signed-in user can mute any individual notification type from a settings page (`/settings/notifications`) so that type is never created for them again.
* A `notification_preferences` table keyed by `(user_id, type)` with an `enabled` boolean, defaulting to enabled for every type when no row exists.
* Enforcement lives in `lib/notifications.ts`'s `notify()`/`notifyMany()` — the single choke point every fan-out path goes through. A muted type is checked before the row is ever inserted, so nothing is written for that user (as opposed to writing it and filtering at read time) — the unread badge count and the inbox list are correct for a muted user with zero extra filtering logic anywhere else, at the cost of not being able to later "unmute retroactively" and see history for the period it was muted.
* `app/api/notifications/preferences/route.ts` (GET the full map + human labels, PUT to toggle one type) is the server-side surface; `app/settings/notifications/page.tsx` is the toggle UI.
Live notification push (6e — done 2026-09-02 nightly build): the unread-badge count in `NavBar` no longer relies solely on a 15s poll. `lib/notificationEvents.ts` is a single in-process `EventEmitter`-based pub/sub (one channel per user id); `notify()`, `markRead()`, and `markAllRead()` in `lib/notifications.ts` all publish the user's fresh unread count to it after writing. `app/api/notifications/stream/route.ts` is a `GET` SSE endpoint (auth required, same `requireUser()` as the other notification routes) that sends an immediate unread-count snapshot on connect, then forwards every subsequent publish for that user as an `event: unread` SSE message, plus a comment-line heartbeat every 20s to keep proxies from timing the connection out. `NavBar.tsx` opens an `EventSource` to that endpoint and updates the badge from each `unread` event; if `EventSource` is unavailable (SSR, or a browser/proxy that doesn't support it) or the connection errors out, it falls back to the original 15s-interval polling for that mount (no reconnect/backoff logic on the SSE side — a deliberate scope cut, see session log).

Tooling notes (read this before re-discovering the same issues)
* This is Next.js 16 — the `create-next-app` scaffold drops a `AGENTS.md`/`CLAUDE.md` pointer at the repo root telling you to read `node_modules/next/dist/docs/` before writing code, because App Router conventions keep changing. Confirmed still true this session: dynamic route `params` (and `searchParams`) are `Promise`s that must be `await`ed (`ctx: { params: Promise<{ id: string }> }`), and `cookies()` from `next/headers` is async (`await cookies()`). "Cache Components" (`cacheComponents: true` in `next.config.ts`) is opt-in in Next 16, not default — this app doesn't enable it, so the pre-16 caching model applies and `export const dynamic = "force-dynamic"` on every route handler that touches cookies/the DB is enough (no `"use cache"` directives needed).
* ESLint flat config for `eslint-config-next@16`: current `create-next-app` scaffolds `eslint.config.mjs` using `defineConfig`/`globalIgnores` from the `eslint/config` package plus `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript` sub-path imports — this shape works out of the box with the `eslint@9` that `create-next-app` itself installs; no manual workaround was needed this session (earlier sessions' notes about `eslint-config-next`'s default export shape and pinning `eslint` below `10.x` may be stale for this scaffold version — re-verify if `npx eslint .` breaks on a fresh install).
* `react-hooks/set-state-in-effect`: a `useEffect` whose body calls a `load()` function declared at component scope (needed when a button handler must also trigger the same reload) gets flagged even though `load()` only sets state after an internal `await`. Fix is a scoped `// eslint-disable-next-line react-hooks/set-state-in-effect` directly above the `load()` call — **the disable comment must be the line immediately before the flagged call**; multi-line explanatory comments have to go *above* the disable directive, not between it and the code, or the directive silently doesn't attach (ESLint then reports both "unused disable directive" and the original error). `NavBar`'s polling effect avoids the whole issue by declaring its loader function inside the effect body itself.
* `next build` type-checking test files: `tsconfig.json`'s default `include` picks up every `**/*.ts`/`**/*.tsx`, which pulls Vitest test files into the Next.js build's TypeScript pass and fails it. Fix: add `"__tests__/**"` and `"vitest.config.ts"` to tsconfig's `"exclude"` array.
* `next.config.ts` cannot carry an `eslint` key in this Next.js version — ESLint config now lives solely in `eslint.config.mjs`.
* `@types/react-dom` doesn't publish a version matching `react-dom`'s own version number — let npm resolve `@types/react`/`@types/react-dom` against their own `^19` ranges rather than pinning to the runtime package's exact version.
* `next/font/google` requires outbound access to `fonts.googleapis.com` at build time — fails hard in a network-restricted sandbox. Use system font stacks (or `next/font/local` with self-hosted font files) instead.
* HTTP integration test spawning a real server: spawn the **local** `next` binary directly (`node_modules/.bin/next start`), not via `npx next start` — `npx` forks a wrapper process that doesn't reliably forward a kill signal on to the actual `next-server` child, which left orphaned servers holding the spare port open between test runs (`EADDRINUSE` on the next run). Spawn with `detached: true` and kill the whole process group with `process.kill(-server.pid, "SIGTERM")` in `afterAll`.
* Same-millisecond `ORDER BY created_at DESC` ties need a secondary sort key — see backlog item #14 above.
* Per-test-file isolated SQLite databases: `lib/db.ts` reads `process.env.SQLITE_DB_PATH` at module-load time (falling back to `data/session-zero.db` for the real app). `__tests__/setup.ts` is wired in via `vitest.config.ts`'s `setupFiles` and assigns a fresh `data/test-<uuid>.db` path before that test file's own imports resolve — Vitest isolates each test file's module registry, so this gives every test *file* (not every individual test) its own DB. The HTTP integration test manages its own separate DB file explicitly (passed via `env` to the spawned `next build`/`next start` child processes).
* `package.json` needs `"type": "module"` for `vitest.config.ts`'s `export default` to load natively without a CJS-compat warning; harmless with `next build`/`next lint`/the test suite since every source file already uses ESM syntax.
* `vitest.config.ts` should use `path.dirname(fileURLToPath(import.meta.url))` instead of bare `__dirname`, which Vite's native config loader warns is unsupported and will eventually be removed.

Design questions resolved before coding, per this item's own backlog text:
* **Who can message whom.** Chose "any signed-in user can message any other signed-in user," no prerequisite relationship. This app already has several ungated, open-to-anyone surfaces — browsing/joining campaigns has no prior relationship requirement, the sub-request volunteer pool (backlog #20) is browsable and volunteer-able by any signed-in stranger, and public player profiles (`/players/[id]`) are visible to everyone. The one hard rule is you can't message yourself.
* **Data model.** A `messages` table (`id`, `sender_id`, `recipient_id`, `body`, `read`, `created_at`) — no separate `conversations` table. A "conversation" is simply the unique unordered pair of `(sender_id, recipient_id)` values across a user's messages, computed at query time rather than tracked as its own row, since nothing about a conversation needs its own identity or mutable state beyond the messages inside it (no title, no archival, no group membership — those would justify a real entity; a 1:1 thread doesn't). This also sidesteps a canonicalization question a `conversations` table would need (e.g. always storing the lower user id first) — every query just checks both directions.
* **Unread tracking "wired into the existing notification system."** Read literally: `sendMessage()` calls the existing `notify()` with a new `message_received` type, going through the same `NOTIFICATION_TYPES`/`NOTIFICATION_LABELS`/preferences/mute machinery as every other notification type, and the NavBar's existing unread badge (SSE + polling fallback, backlog #6e) picks it up automatically with zero NavBar changes needed. 2026-09-07 (live session, continued): implemented backlog item #38 (follow + activity feed).

The design question this item raises head-on: the backlog line's own text says "surfacing their public session-log posts and character milestones" — but session log entries are NOT public. `lib/access.ts`'s `hasPrivateAccess()` gates the session log (plus party notes, table chat) to a campaign's DM and approved/active members, and this boundary already has explicit regression coverage at both the unit layer and the HTTP-integration layer (rendered-HTML content checks across every access role). Building a feed that literally surfaced "session-log posts" for a non-member follower would mean either (a) silently bypassing `hasPrivateAccess` for feed purposes — a real privacy regression dressed up as a feature, or (b) restricting the feed to only followers who also happen to be active members of the relevant campaign, which defeats the entire point of a *cross-campaign* activity feed and doesn't match how a "follow" relationship works anywhere else in this app. Neither is acceptable, so the feed's scope is deliberately narrower than a literal reading of the backlog text: it surfaces only events that are already fully public today, independent of any campaign membership — a character's existence/status on its owner's `/players/[id]` page, and a campaign's accepting-requests/rating state on its own public detail page. This is documented at three levels so it can't be silently "fixed" into a privacy hole later: a comment on `feed_events` in `lib/db.ts`, a comment at the top of `lib/feed.ts`, and this entry.

Two design questions the backlog item's own text raised, both resolved explicitly:

1. **Who can follow whom.** The backlog line says "players/DMs you've actually played with," which reads like it wants a shared-campaign-membership gate. Rejected that reading in favor of the same open-relationship convention already established by backlog #31 (direct messaging): any signed-in user can follow any other signed-in user, no prerequisite relationship. Reasoning: (a) this app has no comparable gate anywhere else — campaign browsing, the sub-request pool, messaging, and board posting are all ungated the same way; inventing one just for follows would be a new, unexplained inconsistency; (b) a real "played together" gate would need to walk shared campaign membership *history*, including past `'left'` memberships, not just current ones — real added complexity; (c) it would buy no actual privacy benefit, since everything a follow can surface is already fully public on the followed user's own profile regardless of who follows them. The backlog phrase is read as describing the expected *use case* (you naturally follow people from your own tables), not a hard technical requirement.

2. **What counts as a feed-worthy event.** Four event types, each hooked at the exact moment it happens rather than derived after the fact by querying mutable rows (a character's `updated_at` bumps on every edit, not just a status change, so it can't double as a reliable "this is when it happened" timestamp — unlike an immutable per-row table like `session_log_entries`, which the existing stats/chronicle code already reads directly):
   - `character_created` — hooked into `lib/characters.ts`'s `createCharacter`, fires unconditionally (a new character is immediately public on its owner's profile).
   - `character_status_changed` — hooked into `updateCharacter`, fires only when status actually transitions into `retired` or `fallen` from something else (not on every edit, and not on a transition back to `active`, which isn't the milestone the character-legacy framing is about).
   - `campaign_became_full` — hooked into `lib/memberships.ts`'s `approveRequest`, fires only on the real open→full transition (checked against `campaign.accepting_requests` as read *before* the update in that same call, so re-approving into an already-full, manually-reopened campaign doesn't re-fire it).
   - `campaign_first_rated` — hooked into `lib/campaignRatings.ts`'s `rateCampaign`, fires only the very first time a campaign receives *any* public rating (checked via the campaign's rating count before the upsert), not on every subsequent rating, to avoid noise.

   All four are written through a single `recordEvent()` choke point in `lib/feed.ts`, mirroring how `lib/notifications.ts`'s `notify()` is the one place every notification fan-out goes through.

Data model: `follows` (follower_id, followed_id, unique pair) and `feed_events` (actor_id, type, optional campaign_id/character_id, a precomputed message, created_at). `listFeed(viewerId, { page, pageSize })` joins `feed_events` to `follows` on `followed_id = actor_id` filtered to the viewer's own `follower_id`, ordered newest-first with the same `rowid` tiebreak convention used everywhere else in this file (same-millisecond ties). One integrity wrinkle surfaced immediately by the test suite: `feed_events.character_id REFERENCES characters(id)`, but unlike campaigns (only ever soft-cancelled, never deleted), characters *can* be genuinely deleted via `deleteCharacter` — the existing "deletes a character" unit test started failing with a `FOREIGN KEY constraint failed` the moment `createCharacter` began writing a referencing feed event. Continuing the owner's "keep completing backlog items back-to-back throughout the day" instruction. Picked #39 next: the next unblocked item in priority order per the previous entry's own note (#3 and #6c remain the hard blockers).

Before writing any code, re-read #39's own backlog text against #35's actual implementation, since the backlog line asserts a dependency ("depends on #35 producing real attendance data") that doesn't hold up: #35's `session_rsvps` table records *intent* to attend the campaign's current `next_session_at` -- confirmed or declined -- not whether anyone actually attended. Worse, it isn't even durable history: `lib/schedule.ts`'s `updateSchedule()` deletes every RSVP row for a campaign the moment `next_session_at` changes to anything else (including back to unscheduled), which is the correct behavior for what RSVP is *for* (an answer for a date that's no longer scheduled is meaningless), but it also means there is no persisted RSVP trail surviving past a single scheduled date to mine for a historical "who showed up" stat once a session has actually happened and the DM moves on to scheduling the next one. This is the same category of problem backlog #18 (personal stats) already hit and solved by cutting scope rather than fabricating data: that item dropped "hours at the table" entirely because no honest data source existed for session duration, rather than inventing a fake number. Reading #39 literally and deriving "reliability" from RSVP data would have meant the same mistake in a different shape -- presenting intent-to-attend as if it were attendance, or reading every session as `null` once its RSVPs got wiped.

Of the two honest paths the task laid out -- (a) a real "mark attendance" affordance tied to session log entries, or (b) a more modestly-labeled proxy computed from RSVP data alone -- (b) turned out not to really be available at all once the RSVP-durability issue above is accounted for: there's no persisted RSVP history left to compute *any* honest proxy from after a session passes. So (a) was the only path that produces real data, and it wasn't actually much more scope than a well-labeled proxy would have been: session log entries are already the one durable, immutable per-session record this app has (used by backlog #18's own "sessions run/played" proxy for exactly this reason), so attendance just needed to hang a small table off that.

Design: a new `session_log_attendance` table (`entry_id`, `user_id`, `attended`, `created_at`; composite primary key on `(entry_id, user_id)`). `lib/attendance.ts` is the new business logic, following this repo's established conventions closely: `attendanceCandidates(campaignId)` returns the active party minus the DM (a DM is presumed present for every entry they themselves post -- they wrote the recap -- so this signal is deliberately scoped to players only, matching the sub-request pool's own "reliability rating requested" framing, which is about players/subs showing up, not the table's own DM); `listEntryAttendance(entryId)` is a no-auth-of-its-own read helper (matching `lib/npcNotes.ts`/`lib/sessionRsvps.ts`'s convention of leaving the access check at the route) returning every current candidate enriched with the DM's recorded value or `null` if nobody has recorded it yet; `setEntryAttendance(entryId, dmId, records)` does a full-replace (mirrors `lib/availability.ts`'s `setAvailabilitySlots` -- the UI always submits the complete current checklist rather than individual toggles), checks `dmId` against the entry's campaign DM itself (matching `lib/sessionLog.ts`'s own authorship check), and rejects any submitted userId that isn't a current candidate rather than silently accepting it; `getAttendanceStats(userId)` is the aggregate `{ recorded, attended, rate }` read, with `rate: null` (not `0`) when `recorded` is `0` -- the same unrated-not-zero convention `lib/ratings.ts`'s `getUserRatingSummary` already established, so a user nobody has ever marked attendance for reads as "no data yet," not as an unreliable 0%.

Wiring: `POST /api/campaigns/[id]/log` (session log entry creation) gained an optional `attendance` array in the same request body -- "when the DM posts a session log entry, they mark which of the currently-active party actually showed up," submitted together rather than as a separate follow-up call. The route validates every submitted userId against `attendanceCandidates()` *before* calling `createEntry()`, so a bad id 400s cleanly rather than leaving a content-only entry behind after a partial failure. A new `app/api/campaigns/[id]/log/[entryId]/attendance/route.ts` (GET + PUT, both DM-only) lets the DM view or fix up an entry's attendance after the fact, for the case where they didn't mark it at creation time or need to correct it. `SessionLogPanel` gained: an optional "Record who attended this session" checklist under the new-entry composer (defaults every current party member to checked -- the DM unchecks whoever missed it, rather than starting from a blank slate that would require checking everyone by hand every time), and a DM-only "Attendance" toggle per existing entry that fetches the current record and lets it be edited/saved. The campaign detail page passes its already-queried `approvedMembers` list straight through as `partyMembers` -- no new query needed, since that list already excludes the DM by construction (it only ever joins the `memberships` table).

Judgment call on where the signal is shown: per-entry attendance ("who missed this specific session") stays DM-only to view, even though the rest of the session log/party notes/chat is visible to the whole active party -- naming a specific missed session is more pointed/potentially awkward than this app wants to surface widely, whereas the aggregate rate is a much softer, already-normalized signal (like a star rating) that's fine to show publicly. So `getAttendanceStats()` is surfaced on `/players/[id]`, right next to the existing "As DM"/"As player" reputation lines, labeled "Attendance (as player)" with an explicit "DM-recorded attendance, not RSVP responses" caption so it's never confused with backlog #35's RSVP feature -- this satisfies the original prototype's own "sub reliability rating requested: 4+*" mocked use case without having to also wire it into the sub-request pool's volunteer list in this pass (a reasonable follow-up, not built here, since a curious requester can already visit a volunteer's public profile).

Known limitation, called out explicitly rather than glossed over (in `lib/attendance.ts`'s own doc comments, in "What the app does today," and here): attendance-marking candidates are always computed from the campaign's *current* active party, not from a point-in-time snapshot of who was actually an approved member back when a given entry was first logged. This app's memberships table only tracks current status (pending/approved/declined/left), not an interval history of who was approved between which dates, so there is no way to reconstruct "who was really on the roster that day" for an old entry -- the same category of gap as backlog #19's campaign chronicle only counting *currently*-linked characters rather than a full historical roster. In practice this only matters when the DM edits attendance on an old entry well after the roster has changed (e.g. marking a brand-new member as having attended a session logged before they ever joined); marking attendance at the moment an entry is first posted -- the common path this pass optimizes for -- reflects the real party at the time, since the roster hasn't had a chance to drift yet.
